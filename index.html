01Open the file

What is in there

The file runs top to bottom: a small label first, then the model's numbers. Click any part to open it — the panel on the right follows you down.

02Mapped, not loaded

The file is never really read

Here's the part that surprises people. The program doesn't copy into memory. It calls mmap — the file gets an address range, and pages arrive only when touched.

The bytes on disk are already in the exact layout the math wants, so there's no conversion step. Nothing to parse, nothing to rearrange.

NoteThis is the same trick a database uses for its data files. Nothing AI-specific about it — it just matters more when the file is enormous.
03Packed small

Why the file fits at all

The weights aren't stored as normal floating-point numbers. They're rounded onto a grid of 16 steps and stored as 4 bits — half a byte each.

Rounding on its own would be too crude. So the numbers are handled in groups of 32, and each group stores its own step size. A group of small numbers gets a fine grid, a group of large ones gets a coarse grid.

The arithmetic is not subtle:

The obvious approach would be to unpack a table back to real numbers, then multiply. That would throw away the entire benefit.

Instead the incoming data gets packed too, and the multiply happens directly on the small integers. One correction at the end restores the scale.

04Running it

Your prompt, then one word at a time

Two different jobs. Your prompt goes through all at once — that's a big batch of multiplications, and it's quick. Then the model produces output one word per full pass, and each pass has to wait for the one before it.

Why

Layers are independent blocks at known offsets, so a runtime can hand the first N to a GPU and leave the rest on the CPU. That is one flag, and it is the single biggest lever on speed.

Every word means reading every weight in the model, once. So the speed limit isn't how fast your chip multiplies — it's how fast it can pull bytes out of memory.

Cut the bytes by four and you get roughly four times the words per second. That's the whole reason the packing exists.

RuleIf the model fits in your fastest memory, it runs well. If it spills, it crawls. That single fact explains most of what you'll read about picking a model size.

Two kinds of attention

The layers differ in exactly one way: how they remember what came before. That single choice is why a million-word context is affordable.

Glossary

tensor
A named block of numbers with a shape. Not a physics concept — a model file is a few hundred of them end to end, and nothing else. The numbers inside are the weights, or parameters: what the model learned.

1 dimension — a list

output_norm.weight is 3 840 numbers in a row. Shape: 3840.

2 dimensions — a table

attn_q.weight is 3840 × 4096 — a table of 15.7 million numbers. Most tensors look like this.

3 dimensions — a stack

ffn_gate_exps.weight is 3584 × 3072 × 896 — 896 tables in one tensor. This is how Kimi stores its experts.

shape
How many rows, columns and sheets a tensor has. Multiply them for the number of weights.
3840 × 4096 = 15.7 million weights
width
How many numbers stand for one token as it moves through the model. Every layer takes a list this long and hands back another the same length — the width never changes from the first layer to the last.
Gemma 12B is 3 840 wide · Kimi K3 is 7 168
weights  (parameters)
The individual numbers inside the tensors — what the model learned during training. "12 billion parameters" just means: add up the cells in every tensor.
not the same as the file's size in bytes
token
A chunk of text. Models never see letters or words — text is cut into tokens and each becomes a number. Roughly 4 characters each.
"understanding" → under · stand · ing
vocabulary
The full list of tokens a model knows, stored in the file as plain text.
Gemma 262 144 · Kimi 163 840
layer  (or block)
One repeating stage of the model. Each layer's output feeds the next. Every layer holds the same kinds of tensor, just with its own numbers.
Gemma 48 layers · Kimi 93
attention
The part of a layer that looks back at earlier tokens to decide what matters. Its tensors are named attn_*.
≈ 20% of the Gemma file
feed-forward
The part that does the bulk of the transforming, one token at a time. Named ffn_*. Usually the biggest thing in the file.
≈ 72% of the Gemma file
norm
Tiny tensors that keep numbers from growing or shrinking out of range between stages. Thousands of values, not millions.
15 360 bytes each
quantization
Storing each weight in fewer bits — rounding it onto a coarse grid to shrink the file. "Q4" means about 4 bits per weight instead of 16.
16 bits → 4 bits = 4× smaller
expert  (mixture of experts)
Instead of one feed-forward block per layer, many alternatives. Only a few run for any given token, so a huge model stays affordable.
Kimi: 896 per layer, 16 run
router
The small tensor that decides which experts handle the current token.
25.7 MB of a 17 GB layer
context
How many tokens the model can hold in mind at once.
Gemma 256K · Kimi 1M
KV cache
The running scratchpad of the conversation so far. Not in the file — memory your process allocates, and it grows with every token.
the thing that fills your RAM
metadata
The key-and-value list at the front of the file: how many layers, how wide, how to turn text into tokens. It is what lets one program run a model it has never seen.
mostly the vocabulary — megabytes, not kilobytes
index
A directory of every tensor in the file: its name, its shape, and the byte where it starts. Like the central directory of a zip.
667 entries in 40 KB for Gemma 12B
family  (architecture)
Which design the model follows. The program reads this first and builds the right shape of network before loading a single weight.
gemma4 · kimi-k3 · llama
offset
The byte position where a tensor's numbers begin. The file lists one per tensor, so anything can be found by arithmetic.
@ 0x21C04000
mmap
Handing the file to the operating system as an address range instead of copying it into memory. Why a 20 GB model opens instantly.
no read, no parse
